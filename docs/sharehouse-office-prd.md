## 1. 프로젝트 배경 및 문제 (Background & Problem)

### 1.1. 배경 (Background)

1. 기존에는 노션 + 계산기로 관리비를 계산하고 카톡으로 관리비를 공지했다.

### 1.2. 문제 (Problem)

1. 일반적으로는 30분이면 정산이 끝나지만, 중도입퇴실이 있는 달에는 일할계산과 여러 번의 검산이 필요해 최대 2시간까지 소요된다.
2. 카톡 공지를 위해서 관리비 표를 캡쳐하고, 노션 링크를 복사하고, 카톡방을 찾아 들어가서, 게시글을 작성하는 과정이 번거롭다.

## 2. 유저 정의 및 스토리 (User Definition & Story)

### 2.1. 유저 정의 (User Personas)

1. Primary: 쉐어하우스 운영자 — 매월 관리비 정산과 입주자 관리를 직접 수행. 한 명의 운영자가 여러 지점(하우스)을 소유하고 관리할 수 있다.
2. Secondary: 입주자 — 본인이 부담할 관리비 내역을 공개 조회 화면에서 확인

### 2.2. 사용 맥락 (User Story)

1. 사용 시점: 매월 관리비 정산일
2. 사용 환경: 데스크탑/모바일 반응형 웹, Google 계정으로 로그인
3. 사용 직전 행동: 가스비·전기세·수도세·인터넷 등 청구서 금액 확인, 입주자 계약기간(입실일·퇴실일) 확인

## 4. 범위 (Scope)

### 4.1. 기능 요구사항 (Functional Requirements)

#### 4.1.0. 지점(하우스) 관리

한 운영자가 여러 쉐어하우스 지점을 소유할 수 있으므로, 정산·입주자 데이터는 모두 특정 지점에 종속된다. 아래 4.1.1~4.1.2의 라우트는 지점 컨텍스트 하위에 위치한다 (예: `/houses/:houseId/settlements/:year-:month`, `/houses/:houseId/tenants`).

##### 요구사항

1. FR-000: 사용자가 지점 정보(이름 등)를 등록하면, 시스템은 이를 해당 사용자 소유의 지점 목록에 저장한다.
2. FR-000-1: 사용자가 여러 지점을 보유한 경우, 시스템은 작업할 지점을 선택할 수 있는 화면 또는 전환 UI를 제공한다.
3. FR-000-2: 사용자는 본인이 소유한 지점의 정산·입주자 데이터에만 접근할 수 있다.

##### 검증 기준 (Acceptance Criteria)

- [ ] 지점 등록 후 목록에서 즉시 조회된다.
- [ ] 지점이 2개 이상일 때, 특정 지점을 선택하면 이후 정산/입주자 화면이 해당 지점의 데이터만 보여준다.
- [ ] 다른 사용자가 소유한 지점의 데이터에는 접근할 수 없다.

> 범위 외: 지점을 다른 계정과 공유하거나 위임하는 기능(초대, 멤버십, 페이지/기능 단위 권한 세분화)은 이번 버전에서 다루지 않는다. 5장 참고.

#### 4.1.1. 정산 대시보드 (`/houses/:houseId/settlements/:year-:month`)

##### 요구사항

1. FR-001: 사용자가 정산월의 관리비 항목별 금액과 청구기간을 입력해 저장하면, 시스템은 별도의 조회 액션 없이 입주자별 부담액을 자동으로 계산한다.
2. FR-002: 시스템은 입주자 관리 화면(4.1.2)에 등록된 입주자의 입실일·퇴실일 데이터를 참조하여, 인원 변동 시점을 기준으로 서브 기간을 자동 분할해 계산한다.
3. FR-003: 사용자가 정산 대시보드에서 정산 결과를 조회하면, 시스템은 입주자별 항목별 금액·총액·이용일수를 표로 보여준다.
4. FR-004: 사용자가 정산 결과를 확정하면, 시스템은 해당 정산월을 확정 상태로 전환하고, 확정 상태에서는 관리비 항목 데이터와 관련 입주자 계약기간이 수정되지 않도록 막는다.
5. FR-005: 사용자가 확정을 해제하면, 시스템은 해당 정산월을 다시 데이터 수정과 재계산이 가능한 상태로 되돌린다.

##### 관리비 정산 계산 로직 (FR-001, FR-002 상세)

1. **항목별 유효기간 결정**
   - 청구서에 시작일·종료일이 명시된 항목(가스비·전기세 등, 정산월과 어긋나는 경우 포함): 청구서에 적힌 기간을 그대로 유효기간으로 사용한다. 정산월 범위로 임의로 자르지 않는다.
   - 정산월 전체를 쓰는 항목(수도세·인터넷 등 매달 1일~말일 청구): 정산월 1일~말일을 유효기간으로 사용한다.
   - 공용물품(구매일만 있고 종료일 없음): 그 달 첫 인원변동 이전 구매 시 정산월 전체를, 인원변동 중간 구매 시 구매일~말일을(구매 이전 서브 기간 제외), 마지막 인원변동 이후 구매 시 구매일~말일을 유효기간으로 사용한다.
2. **서브 기간 분할**: 유효기간을 입주자 구성(거주 인원)이 바뀌는 시점 기준으로 여러 서브 기간으로 쪼갠다.
3. **1일당 단가 계산**: `1일당 단가 = 항목 금액 ÷ 유효기간 전체 일수`. 이 단계에서는 반올림하지 않는다.
4. **서브 기간별 1인당 배분액 계산**: `서브 기간별 1인당 배분액 = 1일당 단가 × 서브 기간 일수 ÷ 그 서브 기간의 실제 거주 인원수`. 이 단계에서도 반올림하지 않는다.
5. **입주자별 항목 합산 및 반올림**: 입주자가 실제 거주했던 서브 기간들의 배분액을 합산한 시점에서 처음이자 유일하게 원 단위로 반올림한다.
6. **입주자별 관리비 총액**: 모든 항목의 (반올림된) 합산액의 합.
7. **오차 처리**: 반올림으로 "입주자별 금액의 합"과 "항목 실제 총액"이 1~2원 차이 날 수 있으며, 별도 보정 로직(최대잔여법 등)을 적용하지 않고 해당 차액은 운영자가 부담한다.
8. **이용일수(참고 지표)**: `이용일수 = 정산월의 날짜 범위와 입주자 계약기간(입실일~퇴실일)의 교집합 일수`. 실제 금액 계산에는 영향을 주지 않는 참고용 표시값이다.

##### 유즈케이스

1. 사전 조건: 입주자 관리 화면(4.1.2)에 입주자 계약기간(입실일·퇴실일)이 등록되어 있다.
2. 정상 흐름:
   1. 사용자가 정산월의 관리비 항목별 금액과 청구기간을 입력해 저장한다.
   2. 시스템이 입주자 관리 화면에 등록된 입실일·퇴실일 데이터를 참조해 자동으로 계산한다.
   3. 사용자가 정산 대시보드에서 계산된 결과를 확인한다.
   4. 사용자가 결과에 이상이 없으면 정산을 확정한다.
3. 예외 흐름:
   - [청구기간이 정산월과 어긋나는 항목(가스비·전기세 등)] → [정산월로 자르지 않고 청구서에 명시된 기간을 그대로 유효기간으로 사용한다]
   - [공용물품이 인원변동 중간에 구매됨] → [구매 이전 서브 기간은 계산에서 제외하고, 구매 이전 퇴실자에게는 배분하지 않는다]
   - [확정된 정산월의 데이터를 수정해야 하는 경우] → [먼저 확정을 해제한 후 데이터를 수정하고, 다시 확정한다]
4. 사후 조건: 정산 결과가 입주자별로 자동 계산되어 대시보드에 표시되고, 확정 시 데이터가 잠긴 상태가 된다.

##### 검증 기준 (Acceptance Criteria)

- [ ] 관리비 항목별 금액·청구기간을 저장하면 별도 조회 액션 없이 자동으로 계산된다.
- [ ] 입주자 관리 화면에 등록된 입실일·퇴실일 데이터를 기준으로 서브 기간이 분할된다.
- [ ] 서브 기간 계산 단계(1일당 단가, 서브 기간별 배분액)에서는 반올림이 발생하지 않는다.
- [ ] 입주자별 관리비 합계가 계산된 후 딱 한 번만 원 단위로 반올림된다.
- [ ] 가스비·전기세처럼 청구기간이 정산월과 다른 항목은 청구서에 명시된 기간을 그대로 유효기간으로 사용해 계산된다.
- [ ] 공용물품은 구매 시점 이후 거주자에게만 배분되고, 구매 이전 퇴실자에게는 배분되지 않는다.
- [ ] 반올림으로 인한 1~2원 차액에 대해 별도 보정 로직이 적용되지 않고 운영자 부담으로 처리된다.
- [ ] 입주자별 이용일수가 계약기간과 정산월의 교집합 일수로 정확히 표시된다.
- [ ] 확정된 정산월의 관리비 항목 데이터와 관련 입주자 계약기간은 확정 해제 전까지 수정할 수 없다.
- [ ] 확정을 해제하면 해당 정산월의 데이터 수정과 재계산이 다시 가능해진다.

#### 4.1.2. 입주자 관리 (`/houses/:houseId/tenants`)

##### 요구사항

1. FR-006: 사용자가 입주자 정보(이름, 계약기간 등)를 등록하면, 시스템은 이를 입주자 목록에 저장한다.
2. FR-007: 사용자가 등록된 입주자 정보(계약기간 포함)를 수정하면, 시스템은 변경된 정보를 저장하고 이후 정산 계산에 반영한다.
3. FR-008: 사용자가 입주자 목록을 조회하면, 시스템은 입주자 이름을 가나다순으로 정렬하여 보여준다.

##### 유즈케이스

1. 사전 조건: 사용자가 로그인된 상태다.
2. 정상 흐름:
   1. 사용자가 입주자 정보(이름, 계약기간 등)를 입력한다.
   2. 시스템이 입주자 목록에 저장한다.
   3. 사용자가 필요할 때 등록된 정보(계약기간 포함)를 수정한다.
3. 예외 흐름:
   - [수정하려는 계약기간이 이미 확정된 정산월과 겹침] → [정산 대시보드(4.1.1)에서 해당 정산월의 확정을 먼저 해제한 후 계약기간을 수정하고, 다시 확정한다]
4. 사후 조건: 최신 입주자 정보가 정산 계산에 반영될 수 있는 상태가 된다.

##### 검증 기준 (Acceptance Criteria)

- [ ] 입주자 등록 후 목록에서 즉시 조회된다.
- [ ] 등록된 입주자 정보(계약기간 포함)를 수정하면 이후 정산 계산에 변경된 값이 반영된다.
- [ ] 입주자 목록이 이름 가나다순으로 정렬되어 표시된다.
- [ ] 확정된 정산월과 겹치는 계약기간은 해당 정산월의 확정을 해제하기 전까지 수정할 수 없다.

## 5. 범위 외 (Non-Scope)

1. 자동 알림 발송: 정산 확정/공지를 자동으로 발송하는 기능은 이번 범위에서 제외하고, 필요 시 다음 사이클에서 재검토한다.
2. 공개 조회 화면(`/view/:year-:month`): 이번 버전에서는 개발하지 않고 다음 단계로 이월한다.
3. 지점 공유/위임: 운영자가 다른 계정을 초대해 특정 지점을 함께 관리하게 하는 기능(멤버십)과, 페이지·기능 단위로 세분화된 권한 부여는 이번 버전에서 제외한다. 이번 버전은 지점 소유자(owner) 본인만 접근 가능한 것을 전제로 한다. 향후 도입 시 기존 데이터 마이그레이션이 없도록, 데이터 모델에는 지점(house) 단위 구분을 미리 반영해둔다.
